# Executor-retirement PR-grind lessons

Use this when removing a production executor or fixing role/authority policy across runtime, manifests, tests, and docs.

Current authority: `coding-workflow-authority-map-v0.1.md`. This procedural guide must not override that policy map.

Closing phase: enter this guide only after steps 1–6 in `executor-retirement-and-policy-convergence.md` pass; return there for postmerge convergence after PR grind.

## Closure order

1. **Inventory every surface before editing.** Search production parsers, wrappers, manifests, consumer pins, status/brief envelopes, role resolvers, current-reference docs/ADRs, copied examples, and historical fixtures. A retired executor may remain only where the policy explicitly permits historical test evidence.
2. **Make the rejection contract explicit.** Test parser rejection, exact fail-closed reasons, empty/invalid config shapes, case and whitespace variants, and authority booleans. Add the contract first and observe expected RED.
3. **Validate aggregate/list paths independently.** A single-role lookup can reject a child `config_error` while `--list-*` still succeeds. List endpoints must scan every normalized child entry, validate child/error shapes, preserve deterministic precedence, and fail closed on any invalid fixed route.
4. **Pin exact trust metadata, not just identity.** Fixed roles must validate selected agent, adapter verification, dispatch blocker, and every mutation/finalization/dispatch flag. A correct agent name with forged trust metadata is still invalid.
5. **Name current policy directly.** When policy changes from “non-Codex” to “Pi-only,” add a `non_pi_*_allowed=false` invariant. Retain the old field only for schema compatibility, and teach every recursive authority validator that the new field is unsafe if true.
6. **Treat current docs as executable policy.** Include current-reference ADRs, active skill text, synchronized authority-map copies, copied config examples, and worker-envelope enums in semantic negative tests. Historical OpenCode prose must be past-tense or fixture-qualified; it cannot appear as a current lane, worker enum, digest-convergence item, or mutating mode.
7. **Close runtime-byte changes before PR grind.** For fixed-point resealing and downstream manifest validation, follow `executor-retirement-and-policy-convergence.md`; PR grind starts only after that closure passes.
8. **Freeze the exact candidate.**
   - Refresh the base with `git fetch --no-tags origin refs/heads/main:refs/remotes/origin/main`. Audit attributes and clean/process filters before staging or status: reject every `.gitattributes` or `info/attributes` file before any worktree-facing Git operation, and reject any configured `filter.<name>.clean` or `filter.<name>.process` driver. Inspect `git -c core.fsmonitor=false ls-files -v` and reject every assume-unchanged or skip-worktree entry before staging. Pin `core.fsmonitor=false` on every candidate worktree/index Git probe.
   - Only after that audit passes, stage every intended new path with `git -c core.fsmonitor=false -c core.autocrlf=false -c core.eol=lf -c core.attributesFile=/dev/null add -- <paths>`. Read and record the entire two-column output of `git -c core.fsmonitor=false -c core.autocrlf=false -c core.eol=lf -c core.attributesFile=/dev/null status --porcelain=v1 --untracked-files=all --ignore-submodules=none`: block every tracked index/worktree divergence and every untracked path so tests execute the same tracked bytes that will be committed. Inspect ignored state with `git -c core.fsmonitor=false -c core.autocrlf=false -c core.eol=lf -c core.attributesFile=/dev/null status --porcelain=v1 --ignored=matching --untracked-files=all --ignore-submodules=none` and block every ignored path before testing; do not let generated configuration, modules, fixtures, or build artifacts influence the suite outside the candidate. Require `git merge-base --is-ancestor origin/main HEAD` to pass; otherwise rebase before freezing. Record the base SHA from `git rev-parse origin/main` beside the candidate hash.
   - Before snapshotting, fail closed on `.gitattributes`, `$GIT_DIR/info/attributes`, or configured diff drivers that can select a driver, and run from the repository root. Freeze the staged candidate with `git --no-pager -c core.fsmonitor=false -c diff.algorithm=myers -c diff.relative=false -c core.attributesFile=/dev/null diff --cached origin/main --binary --no-color --full-index --no-renames --no-indent-heuristic --submodule=short --src-prefix=a/ --dst-prefix=b/ --unified=3 --no-ext-diff --no-textconv`. This reads indexed blobs instead of invoking worktree clean filters, disables global attributes plus external diff/textconv helpers, prevents cwd-relative path omission, and pins deterministic format choices.
   - Reconcile the frozen artifact path set against a separately captured, root-scoped, `diff.relative=false` staged path inventory, then record hash and line count. Run a secret/private-path scan on the frozen bytes before any external handoff; when binary files are in scope, justify `--binary` and inspect every `GIT binary patch` path out-of-band regardless of whether its encoded blocks are literal or delta, recording the result, or exclude those binaries for separate delivery. Run immutable review against that exact file, then verify the live staged diff still hashes identically before commit.
9. **Restart the PR grind after every head change.**
   - After every head change, return to step 8: repeat the fetch, ancestry, base-SHA, full-status, staging, and staged-hash checks, re-freeze the exact candidate, and regenerate the immutable review artifact before re-running the full suite, focused closure, static scan, readiness, required checks, unresolved-thread query, and mergeability check.
   - Inspect unresolved threads, inline comments, issue comments, and full aggregate review bodies independently. An actionable outside-diff finding may exist only in a body attached to an older head commit; keep a body-only finding ledger until each finding is fixed with expected-RED evidence or explicitly rebutted. A later green reviewer check and zero unresolved threads do not prove closure. Do not treat a helper/check clean result as sufficient.
   - A prior green bot/check result is stale after force-push. Resolve a thread only after the fix is pushed and replied to.
10. **Verify before cleanup.** After merge, follow step 8 of `executor-retirement-and-policy-convergence.md`; only then remove worktree and topic branches.

## Pitfalls

- A bot check marked “pass” because it was rate-limited is not a fresh review verdict; rely on the exact immutable review plus live unresolved-thread inspection and required-check policy.
- A draft PR can make a review bot report `Review skipped`. Green CI plus zero threads is still not a current-head review; use the bot's supported explicit review trigger (or mark the PR ready when appropriate), then inspect the resulting aggregate body and live threads before merge.
- Treat Draft→Ready as a review-boundary event even when the head SHA is unchanged. It can wake reviewers that never ran on the draft and create new current-head findings after every earlier check was green. Do not mark ready and merge in one uninterrupted step: wait for all newly started checks/reviews to settle, then re-enumerate aggregate review bodies, inline/issue comments, and live unresolved threads. If the head did not change, the frozen candidate remains valid, but live review/check closure must be re-established.
- Some review integrations expose a `null` check status even after posting an aggregate review. Do not infer pass or failure from that field: bind completion to the reviewed head in the aggregate review/comment, enumerate every live thread, and keep CI-required-check closure as a separate signal. Prefer the repository's canonical check-status helper or `gh pr checks` exit codes over a homegrown JSON poller.
- A frozen-diff digest is meaningful only with its canonical diff command and option set. An ad-hoc `git diff base head | sha256` may produce different bytes without any source drift. Re-run the exact pinned freeze command, compare the artifact byte-for-byte plus its path set, and report the canonicalization instead of treating a plain-diff hash mismatch as evidence.
- Diff-hunk tunnel vision can produce a false test finding when an unchanged whole-file assertion is satisfied outside the shown hunk. Verify the exact asserted literal against the whole file and run the smallest relevant test before changing a frozen candidate. Prefer a genuine lead/backstop rerun that includes whole-file context; do not add duplicate prose merely to appease the reviewer.
- Treat a user-only Litmus skip as a last-resort, one-shot manual escape hatch for a proven false positive—not as a substitute for tests or review. The user must create it. Once created, invoke the exact guarded command immediately: monitor/search/status/tool calls can consume the one-shot token before the intended action. If that happens, do not recreate it as the agent; either ask the user to re-arm it or take the full no-bypass review path.
- In a strict read-only review, do not use commands that can materialize Git objects or refresh metadata (`git write-tree`, `git hash-object -w`, `git update-index`, or refresh-capable index operations). Read an existing commit tree with `git rev-parse '<sha>^{tree}'`; never create an index tree merely to identify it.
- Block every ignored path for the initial candidate freeze and exact test run. After a trusted Litmus/PR gate, however, authenticated `.claude/*.local` verdict markers may be required state rather than candidate bytes: inventory an exact allowlist, prove the tracked worktree and base-to-head diff are clean, and scope only those markers out. Remove rebuildable pytest/bytecode caches after their owning process exits; never exempt generated source, config, fixtures, or unknown ignored paths.
- Bind the verdict to the frozen artifact, not to a live worktree or index that another process can change mid-review. Hash the artifact first and again before verdict; reconstruct candidate postimages from the pinned base plus that artifact in memory. Treat later worktree/index drift as outside the reviewed bytes, report it, and never silently substitute `git show :path` or current worktree content for the frozen candidate.
- Shape checks are not truth checks. A semver and 40-hex regex may keep wording durable, but status provenance still needs direct evidence: verify a documented base tree with `git rev-parse '<commit>^{tree}'`, bind trust pins to the manifest, and require an authoritative captured observation for an installed commit. If that observation cannot be substantiated, reject the claim rather than accepting a well-shaped SHA.
- Historical commit→tree contracts must distinguish unavailable history from corrupted authority. Run the object lookup without an automatic exception; when it succeeds, assert the relationship. When it fails, relax only for a positively identified shallow checkout or genuinely absent repository metadata/source archive, and keep the rest of the chronology assertions active. A full non-shallow checkout with a missing object must still fail, and an arbitrary Git error must never be treated as an archive signal. Reproduce both sides: a depth-limited checkout passes, while a full checkout with a typoed commit still fails.
- A hostile clean-filter control must force Git to read file content: rewrite a tracked file with different bytes but the same byte length as its indexed blob, and assert that invariant in the test. A size change can let `git status` classify the path as dirty from stat data alone without invoking the filter, making the control flaky.
- Cleanup is scoped to artifacts owned by the current delivery. Inventory pre-existing worktrees and branches before starting; after merge remove the owned topic artifacts, but preserve and report unrelated dirty WIP instead of asserting that the whole repository has only one branch or worktree.
- A status document cannot name its own future squash commit. Label the verified implementation base as immediately preceding the docs-only refresh; validate separate live-observation and trust-pin claim shapes without hard-coding a transient installed version or requiring observed and pinned versions to differ.
- A status-claim rewrite can have several contract consumers. Search the whole contract tree for the old wording before freezing, and keep semver/commit parsing in one manifest-backed authority test; chronology or inventory tests should assert only their own concern instead of duplicating that parser. A focused green on one consumer does not replace the exact full suite.
- Manifest equality is not format validation: if a malformed version is copied into both manifest and status, a broad capture plus equality can false-green. Constrain observed and pinned version captures to the same semver shape, then keep the manifest equality assertion. Prefer the one-line capture tightening over a new parser/helper when numeric semver is the entire contract.
- Updating only a README leaves active ADRs, status docs, skill references, or copied JSON examples contradictory.
- `coding_agent=pi` does not prove fixed primary/secondary/fallback route metadata or list-path safety.
- A full suite from the prior frozen hash is supporting evidence, not final-candidate evidence after another edit.
- If the execution safety layer blocks an irreversible delivery action and explicitly says not to retry or route around it, preserve the verified candidate and request fresh, explicit Delivery Mode authorization. Do not rephrase the command, switch tools, or treat an earlier general “continue” as consent for that blocked side effect.
- Put Claude/Busdriver finalizer prompts that contain Markdown backticks, regexes, quotes, or shell metacharacters in a runtime prompt file and read that file into `claude -p`; do not inline them inside a double-quoted shell argument. This avoids command substitution and unmatched-quote failures without changing the requested operation.
- Do not report merged, post-merge verified, or cleaned until each side effect is observed directly.
